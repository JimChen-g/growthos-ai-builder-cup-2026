## 1. 本次交付边界

将现有 GrowthOS 的“业务证据 → 优先级判断 → 两项行动建议 → 人工审批 → 执行记录”部署为可公开体验的 Google Cloud 原型，展示它如何减少创始人和运营团队在整理信息、制定行动和核对执行记录上花费的时间。

保留现有 SaaS 业务样例、Next.js、FastAPI、LangGraph，以及简体、繁体和英文界面。参赛适配使用独立配置和样例工作区，不把产品整体改成零售系统，不迁移个人真实广告账户，不改动已有真实投放流程。

比赛版采用以下组合：

| 部分 | 本次实现 |
|---|---|
| 前端 | 标准 Firebase Hosting，发布 Next.js 静态导出结果 |
| 接口 | Cloud Run 运行 FastAPI；Hosting 将 `/api/**` 转发到后端 |
| 身份 | Firebase 匿名身份的一键体验；服务端派生独立演示会话 |
| 持久化 | Firestore 保存会话工作流、审批、事件、快照和共享配额 |
| AI | Gemini on Vertex AI，以 Cloud Run 服务账号认证 |
| 敏感配置 | 优先无密钥服务账号；确有必要的固定密钥通过 Secret Manager 注入 |
| 广告执行 | 保留演示写入适配器，明确标注模拟执行；评委不连接个人账户 |

核心 AI 交付不能只把规则结果润色成简报。Vertex AI 必须根据指定证据集提出优先级和两项行动，返回可核对的证据编号，且由服务端验证。事实指标、审批限制和执行权限仍由现有代码约束。

## 4. 效率测试协议

目的：验证团队工作流程是否更省时且仍有可核对依据，不用主观“更智能”代替结果。

### 输入与比较条件

固定同一份脱敏 SaaS 样例，包含收入／广告指标、客户反馈、相关日期和稳定证据编号。人工基线与 GrowthOS 使用完全相同的输入和任务目标；人工基线使用通常的文档／表格整理方式，不额外获得已整理答案。测试前冻结样例及验收标准，允许一次不计时练习。

| 任务 | 人工基线交付 | GrowthOS 交付 | 必须核对 |
|---|---|---|---|
| T1：整理当天简报 | 从原始材料整理关键事实、异常及出处 | 生成带来源的简报 | 事实与数字正确；不能把旧日期数据称为当天观测 |
| T2：决定先做什么 | 比较问题并提出两项行动与依据 | Vertex 输出优先级、两项行动及证据编号 | 每项行动有输入支持；引用准确；未把预测当结果；人工能理解选择理由 |
| T3：核准并核对一项行动 | 在标准审批表中审阅、批准并记录结果与理由 | 审阅同一行动，经审批完成模拟执行并查看事件记录 | 批准内容与执行内容一致；审批人／会话、时间、理由和结果可追溯；明确模拟执行 |

每个任务至少做 **3 组配对重复**：一组包含人工基线和 GrowthOS 各一次。因此完整最小测试是 3 个任务 × 3 组 × 2 种方式，共 18 次。每组使用相同输入；交替进行两种方式，并记录操作者及顺序，避免总是先做人工导致学习效应。若由同一人重复完成，应明确报告这一限制。

每次记录：

1. 从开始阅读输入到交付可接受结果的总时间，包含等待、校验、修正和失败重试。
2. 按统一定义计数的操作步骤，例如打开资料、复制一次证据、完成一次表单、触发一次分析或审批；不把每次击键算成一步。
3. 引用正确性：逐一检查证据编号是否存在、是否支持相应陈述；记录正确引用数／全部引用数，同时单列缺少来源的事实陈述。
4. 任务完成情况、事实错误、遗漏、人工修改次数、是否使用降级模板，以及使用的应用版本和模型 ID。

先保留逐次原始结果，再报告每任务的时间和步骤中位数及范围；可附配对差值。只有实测结果存在且比较条件一致时，才计算相对变化。若未完成测试，材料使用“设计目标／待验证”，**不填写节省 X% 时间、提升 X 倍效率等数字**。3 组重复只够证明原型可测，不足以代表所有企业或建立统计显著性。
